# 菜单栏语音粘贴箱 MVP

## 范围与操作约定

- macOS 菜单栏常驻入口，独立弹出面板：待处理/全部、搜索、原文/最终文本、点击粘贴、仅复制、删除。
- 所有听写先保存原始转录；润色完成更新同一条记录。提前使用原文会消费该条自动投递资格，润色结束不再重复粘贴。
- 手动模式只保存；自动模式恢复本次绑定的目标后投递并发送完成通知，点击仅返回位置，不重复粘贴；半自动模式发送独立通知，点击恢复位置并粘贴。通知 identifier 对应记录 UUID，标题带递增编号。系统控制通知展示顺序，应用提供按编号顺序处理入口。
- 默认手动模式。每次开始听写时冻结投递模式并独立记录原位置；处理中的记录不随设置切换。移除固定目标及额外的记录/打开快捷键，保留可配置的录音快捷键。
- 顶部栏图标打开粘贴箱。面板默认使用打开前的位置，也可选择本条原目标或最近 10 个目标；这只影响手动点击本条，不改变后续听写的起点。
- “完成通知”默认开启，可在设置和粘贴箱切换，关闭会移除本应用的已投递及待发送通知。自动模式仍自动粘贴，半自动模式保留为待处理内容，用户从粘贴箱操作。
- PyObjC 访问 macOS Accessibility，保存应用/窗口/控件身份、UTF-16 文本选区、内存中的局部文字上下文。恢复完全通过 AX 属性与动作完成，不通过屏幕坐标定位。
- 无法唯一确认目标、原选区附近文字变化、窗口失效或权限不足时停止自动粘贴，保留记录并显示原因。MVP 不跨应用或辅助进程重启恢复旧控件引用。
- 内容保存在本机 SQLite；已投递和已复制内容可再次使用。清理只由用户执行，待处理内容不会因为历史数量上限而删除。

## 实现顺序

1. 增量建表、设置和状态转换；记录 UUID、显示编号、原文/最终文本、目标快照、错误及版本。
2. Rust 本地服务管理常驻 PyObjC 辅助进程：目标捕获/恢复、选区校验、剪贴板保护。Objective-C 层负责菜单栏、UserNotifications 按 ID 回调。
3. 将听写流水线接入持久化粘贴箱；每次操作带记录 ID 和版本，自动投递、通知点击与手动点击共享串行投递入口。
4. 菜单栏与 React 面板通过服务接口/Hook 集成；事件只触发刷新，数据库为内容事实来源。
5. Rust 状态/存储测试、前端业务行为测试、构建检查；macOS 验证菜单栏焦点、准确选区、通知点击和失败回退。

## 实现选择与边界

系统操作使用 Rust 通过 stdin/stdout JSONL 调用 PyObjC 辅助进程，复用现有随应用打包的 Python 3.11。依赖固定为 PyObjC 12.2.2 的 core、Cocoa、Quartz、ApplicationServices、CoreText 包；当前不需要额外加入 PyAutoGUI。主界面不直接调用系统 API。浏览器适配层只支持预览和本地历史，不模拟跨应用粘贴成功。

PyObjC 负责系统 API 的类型桥接；本项目负责目标生命周期和文本位置语义。每个请求有独立编号、串行处理与超时。请求超时或通信中断会销毁辅助进程，旧目标 ID 失效；取消录音只放弃该次目标的消费，不中断正在执行的 AX 请求，避免使其他队列目标失效。粘贴请求通信中断标记为结果不确定，不重放请求。

录音快捷键入口立即读取前台 PID 和键盘按下/鼠标点击计数，冻结模式，生成本次录音 ID 并启动独立 AX 采集任务，然后才投递录音启动指令。指令携带该任务，后台不重新选择目标。麦克风就绪即可进入听写，录音提示不可获取焦点；采集未完成时显示“正在记录原输入位置”。转录完成后等待该次采集结果，再将其绑定到粘贴箱条目并进入润色、自动投递或通知流程。每条任务有自己的结果通道，取消和下一次录音不共享目标；迟到的采集结果不能更新其他录音状态。

AX 查询仍是跨进程异步操作，不等于硬件按键发生瞬间的原子快照。采集前后检查原 PID、控件、文本和选区，并与入口保存的输入计数核对；如果采集尚未完成就发生新的键盘输入或点击，则保留转录并报告原因，不能将后来的位置作为起点。计数不包含鼠标移动及修饰键释放，也不代替对应用自行改变焦点的 AX 一致性检查。采集失败仍保留录音能力。

菜单栏和全局快捷键打开粘贴箱仍先捕获当前输入框，再显示面板；H-VibeRec 主窗口与外部应用使用同一路径。设置页的“打开粘贴箱”按钮只打开面板，不推测点击按钮之前的光标。切换模式不重新捕获光标，只影响下一次录音。

焦点查找依次使用应用、所属进程的系统焦点、窗口焦点，以及原窗口中明确标记 AXFocused 的可编辑子控件。子控件搜索有时间和节点上限，不使用“唯一输入框就是焦点”的推测，也不按名称或坐标选择目标。初次查找失败时，只对应用声明且允许设置的 AXManualAccessibility/AXEnhancedUserInterface 开关请求完整辅助功能树，最多在 1.2 秒的捕获预算内等待；不点击 AXWebArea 来触发焦点。捕获和恢复采用相同的焦点判定路径。

macOS 修饰键快捷键监听在事件 tap 被系统禁用后重新启用，并以 20 ms 周期读取系统修饰键状态作为回退。回调与轮询共享按下锁存，按住不重复触发，释放后可再次触发。录音启动、快捷键注册和预热读取运行配置时不访问钥匙串；仅在实际需要 AI 润色凭据时读取密钥。

控件恢复先校验存活进程、原窗口、文档/网页和控件身份。旧 AX 引用失效时，只在原文档中按非空 AXIdentifier、role/subrole 找到唯一匹配后重新绑定；不按标题或子节点序号猜测。所有写入先检查可写能力并处理 AX 返回错误；恢复后读回焦点与选区，粘贴前再次检查。

macOS 原生 NSTextView 即使声明支持 AXIdentifier，也可能在未设置标识符时返回通用错误 -25200。0.2.2 对这一可选属性的特定错误按“无标识符”处理，继续使用存活的 AX 控件引用和可验证选区；控件重建时仍拒绝无稳定标识的重新绑定。权限、通信、失效引用以及关键选区属性错误继续返回失败。

文字内容相同时使用原 UTF-16 选区。其他位置被编辑时，仅在选区附近上下文唯一且完整匹配时重新定位。一次粘贴读回校验成功后，对同一控件中的其他目标更新偏移，支持同一位置多条听写按实际点击顺序追加；与被替换区间重叠的其他选区失效。自动通知另存已插入内容末尾的返回位置，后续在同点追加不会把旧通知移到新内容末尾。返回操作不访问剪贴板、不发送粘贴按键。上下文只保留在辅助进程内存，不进入数据库、日志或 JSONL。

当前范围是原应用、窗口和输入控件仍然存在时的选区恢复。支持可读文本、可写 AXSelectedTextRange 的 AXTextField/AXTextArea/AXComboBox/AXSearchField，以及明确声明 AXEditable 的其他控件。目标可用性检查原窗口是否仍在应用窗口列表中；最小化窗口先还原，再激活原应用、抬起原窗口和恢复控件。AXSelectedTextMarkerRange 是可选恢复路径，最终仍按数值选区校验；仅暴露 Text Marker 的复杂编辑器还不在本次已实现范围。密码框、多光标、不连续选区和无法唯一识别的重建控件会保留到粘贴箱。

窗口还原、应用激活和切换空间是异步操作。恢复允许在 2.5 秒内重试这些焦点操作的 AX CannotComplete 错误，并读回原窗口和原控件的实际焦点；文字粘贴本身不随这些重试重复发送。捕获等待辅助服务锁最多 800 ms，避免启动时短暂的状态查询抢占导致直接丢失目标；等待后仍校验开始时记录的前台 PID。

H-VibeRec 自身输入框同样通过辅助进程访问 AX。启动时按 Tauri 提供的原生窗口引用，为主窗口设置固定 AXIdentifier；辅助进程允许这个主窗口中的可编辑控件，拒绝同进程的录音提示、粘贴箱及未明确登记的工具窗口。窗口判断不依赖显示标题，也不再一律排除 H-VibeRec 的进程。

macOS 通知使用 UserNotifications 原生 delegate。普通 Tauri 桌面通知插件不能满足每条通知的动作回调要求。完成通知开启时，选择自动/半自动会请求通知授权，也可点击“启用系统通知”再次检查。每次提交前读取最新系统权限，按记录 UUID 等待系统提交回执；权限拒绝、提交失败或 5 秒内无回执时保存原因。通知错误不会抢占目标焦点。提交与手动投递、删除串行化，避免已处理条目迟到通知。系统接受通知不等于已展示横幅，勿扰及横幅设置仍由 macOS 控制。通知功能需要有 Bundle ID 的 .app 运行环境；开发二进制不能冒充通知已发送。

精确恢复以可验证的输入控件与选区为准。应用激活、窗口恢复与 CGEvent 发送不构成“文字已被目标应用接收”的证明；能读回时验证结果，不能验证时标为“已发送粘贴”，不自动重试不确定的投递。

权限由实际执行 AX 的 Python 辅助进程检查。设置页和粘贴箱的授权按钮都调用该进程的 AX 授权请求。开发环境的系统授权项可能显示 Python、Code 或 Terminal；正式包的权限归属及签名必须在打包验收中确认。

0.2.9 起录音与后处理独立：停止录音只等待麦克风收尾与 WAV 保存，然后返回任务 UUID/编号，立即允许录制下一段。每段在开始时冻结位置、投递模式、ASR/润色设置。转录使用单个常驻模型依次执行；润色最多两段并行，并与后续转录重叠。所有任务通过原编号更新粘贴箱，后台状态不会覆盖当前录音提示。

自动回写按录音提交顺序执行；前一段润色未完成时，后段就绪内容等待。开始采集位置前即取得录音保护，录音结束后留出 600ms 连续录音间隔，再允许后台改变焦点。等待中的回写不会阻止新的录音；已开始的窗口恢复/粘贴是不可拆分的短操作，此时按录音快捷键会明确提示稍后重试，避免记录一个正在切换中的错误目标。半自动通知点击也会等待当前录音结束。当前段取消仅释放麦克风，不取消已提交任务。

任务在转录前登记到 SQLite，因此粘贴箱可显示排队、准备模型、转录、润色、等待自动回写及错误。转录成功且原文入库后清除该段临时音频；转录失败或重启中断时保留 WAV，支持按同一 UUID 重试。重试采用当前 ASR/润色设置，保留原投递模式和目标；原目标不能跨辅助进程重启恢复，必要时用户从粘贴箱选择新位置。删除失败条目同时删除该条保留音频。润色失败/超时保留原文；不确定的粘贴不自动重放。

录音、队列调度和系统写入作为现有 Rust 本地语音服务的内部能力运行，不依赖面板是否打开；React 通过服务接口提交/重试任务并协调呈现。没有新增远端录音或跨应用控制服务。

## 验收

- 原始结果已经保存时，即使润色/投递失败或重启，也可复制原文。
- 两条结果 A/B 的通知按 B/A 点击，仍分别执行 B/A；重复通知回调不得重复写入。
- 手动复制或粘贴原文后，润色完成不会再次通知/自动粘贴。
- 打开粘贴箱前的光标与听写原目标可独立选择，打开面板不会覆盖任务目标。
- 中文、Emoji、选中替换、窗口移动、文本变化、目标关闭、权限撤销、多显示器逐项验证。
- 已有数据不因版本号变化被清空。启动恢复中断的润色与不确定投递，只恢复可操作状态，不自动重放。

终端后续方案须区分“恢复同一会话并向该会话当前输入点发送”与“恢复终端内部历史输入光标”：前者可评估终端会话 API，后者需要 shell/终端应用自身的编辑状态支持，不能由通用 AX 选区 setter 保证。此结论基于本机日志及上游源码，未在用户终端执行自动测试。

### 0.2.6 通用窗口身份与后台恢复（2026-09-10）

- 原位置新增 `CGWindowID` 和 `proc_pidinfo` 进程启动身份。`window_identity.py` 通过 PyObjC 动态桥接 `_AXUIElementGetWindow`，并用公开的 `CGWindowListCopyWindowInfo(kCGWindowListOptionAll)` 核实窗口所有者；包括后台和屏幕外窗口。桥接符号属于未公开接口，单独封装并作能力检测；符号不可用时保留原 AX 引用路径，不按标题、坐标或控件顺序替代窗口。打包资源和运行时检查已包含新增模块。

## 开发与复验

正常准备和启动：

```bash
npm run runtime:ensure
npm run tauri dev
```

只验证 AX 模块时，可在隔离的 Python 3.11 环境安装 `sidecars/pastebox_ax/requirements.txt`，执行：

```bash
python3 -m unittest discover -s sidecars/pastebox_ax -p 'test_*.py' -v
python3 sidecars/pastebox_ax/main.py --check
```

`--check` 不会请求权限或读取外部应用，只检查真实 AX 类型桥接及权限状态。开发构建支持 `HVR_AX_PYTHON=/绝对路径/python3` 指定独立解释器；发布构建始终使用打包运行时。

开启目标捕获日志：

```bash
RUST_LOG=info,voice_vibe_local_lib::pastebox=debug npm run tauri dev
```

成功捕获日志包含目标 ID、进程 PID、应用、窗口标题、控件角色、查找路径与 UTF-16 选区。相同元数据保存在该条记录的目标中；原输入框文本上下文仍只保留在辅助进程内。窗口存在但输入控件不可用时，会返回独立的错误，而不是笼统提示“窗口与控件不存在”。

真实原生 AX 回归（会创建两个独立测试输入窗口，完成后退出测试进程）：

```bash
ax_fixture_dir=$(mktemp -d /private/tmp/h-viberec-ax-fixture.XXXXXX)
swiftc scripts/debug/AXFixture.swift -o "$ax_fixture_dir/AXFixture"
runtime/asr/bin/python -B scripts/debug/check-ax-fixture.py "$ax_fixture_dir/AXFixture"
```

真实录音入口与投递联合检查（仅 debug/macOS 编译；独立临时数据库和测试窗口）：

```bash
target_qa_dir=$(mktemp -d /private/tmp/h-viberec-target-qa.XXXXXX)
swiftc scripts/debug/AXFixture.swift -o "$target_qa_dir/AXFixture"
# 先保持 npm run dev 的本地前端可用，并完成 cargo build。

```

报告为临时目录的 `target-audit.json`，以其中 `passed` 判断是否通过，不依赖 Tauri 进程退出码。检查调用真实 start_dictation 并启动麦克风，从录音状态中取出该次独立的目标任务并等待采集结果；随后取消录音并注入固定测试转录，经生产粘贴箱投递入口检查跨应用、窗口移动、改变当前选区、最小化、通知 B/A 及重复回调、手动队列与同进程多窗口、WKWebView textarea、窗口关闭和 H-VibeRec 自身的三种编辑器。还验证隔离环境注册的系统快捷键事件、录音指令延迟接收，以及挂起目标采集时的录音/取消/下一次录音。可增加 `HVR_AX_AUDIT_ONLY_SELF=1` 只检查自身编辑器与工具窗口排除。音频不保存，ASR/润色及操作系统通知横幅不在这个检查范围内；通知部分执行的是原生通知事件的生产回调。检查只控制它自己启动的 AXFixture 和独立测试进程内的编辑器，不操作用户文档。

## 微信与 VS Code 兼容路径（当前工作树）

最近现场日志显示，微信失败发生在目标捕获阶段：微信主进程可以返回窗口，但不返回 `AXFocusedUIElement` 或可写的 `AXSelectedTextRange`，因此严格 AX 路径无法得到光标，旧实现不会进入粘贴阶段。VS Code 切换到另一个窗口时则会被窗口/控件身份校验拒绝，这是为了避免把异步结果写入用户后来选择的窗口。

当前增加了 `foreground_paste` 目标能力。捕获时仍使用 macOS Accessibility 查询应用和窗口，并通过 WindowServer 的窗口编号固定目标；只有在应用没有可用编辑 AX 控件、但窗口编号可确认时才创建该能力。投递前先恢复同一 PID 的同一 WindowServer 窗口，再确认它处于前台，然后执行剪贴板写入与 `Command+V`。因为这类应用不提供可读取的文本控件，回执明确为“已发送但未校验”，不会把它计入可验证的 AX 成功，也不会在窗口切换后猜测其他输入框。

该路径不声称恢复微信内部的精确 UTF-16 光标；它恢复的是录音开始时的前台窗口和用户在粘贴时仍保持的当前输入焦点。若微信切换了聊天、打开搜索框、切换到其他窗口或应用，内容会保留到粘贴箱，避免误写。精确 AX 应用仍继续使用原有控件、文档和选区校验。

本机 `~/Documents/Voice Vibe Local/app.sqlite` 的最近记录也印证了原问题：#55–#58 没有目标；#60、#64–#69、#72、#74–#75 已发送但 AX 回读未确认；#73 报告“控件已重建且没有稳定标识”；#70 是前一条未确认结果触发的防重复拒绝；系统设置窗口 #61–#62 返回 AX -25205。旧记录中的 `target_json` 没有 `capability` 字段，升级后新捕获的 AX 不透明窗口会明确记录 `foreground_paste`，便于区分“未捕获”“已发送未校验”和“精确 AX 失败”。
